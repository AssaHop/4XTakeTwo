## Главный вывод

**Там нет захардкоженного правила "атаковать группой если суммарный урон
убьёт".** Вместо этого используется другой фундаментальный приём:
действие оценивается через **симуляцию на копии состояния**, а не через
прямой анализ цели. Пример (`MilitaryFunc.java`, фича `DAMAGE`):

```java
case DAMAGE:
    GameState gsCopy = gs.copy();
    int currHP = target.getCurrentHP();
    new AttackCommand().execute(act, gsCopy);   // проиграли атаку на копии
    int nextHP = target.getCurrentHP();
    int diff = nextHP - currHP;
    if (nextHP <= 0) diff -= 100;               // бонус если добивает
```

Более полные агенты (`OneStepLookAheadAgent.java`) делают то же самое для
ЛЮБОГО действия: копируют `GameState`, применяют действие, оценивают
результат глобальной эвристикой (`StateHeuristic`), берут лучшее.

**"Групповая добивающая атака" в этой системе получается бесплатно,
эмерджентно**, а не специальным правилом: юниты одной стороны решают и
ПРИМЕНЯЮТ действия по одному, не все сразу от одного замороженного
снимка состояния. Юнит A бьёт цель → состояние реально обновляется →
юнит B на следующем шаге СВОЕГО решения видит уже подбитую цель и
получает бонус "это добьёт". Никто заранее не считал "хватит ли урона
троих вместе".

## Структурный разрыв в нашем коде (найдено при сверке)

`src/ai/fsm/states/attackState.js` → `execute()`:

```js
for (const unit of myUnits) {
  const action = this.decideAction(unit, allTargets); // allTargets — общий список, HP не меняется
  actions.push(action);
}
return actions; // применяется ПОЗЖЕ, всё сразу, в aiManager.js
```

Все действия для ВСЕХ юнитов одного AI считаются от одного и того же
замороженного списка целей, и только потом весь пакет применяется
(`aiManager.js: for (const action of actions) await executeAction(...)`).
Это и есть причина, почему у нас сейчас структурно не может получиться
"второй юнит видит, что первый уже подранил цель" — не нехватка
эвристики, а порядок исполнения.

## Три портативные эвристики из SimpleAgent.java (без поиска/симуляции)

Из простого, не-поискового агента (`SimpleAgent.java: evalAttack/evalMove`)
— то, что можно перенести буквально, без архитектурных изменений:

1. **Осторожность дальнобойных юнитов**: если ответный удар врага попадёт
   по нам (мы в его радиусе) и его ATK > нашей DEF — не атаковать, даже
   если цель выгодная по другим критериям.
2. **Отступление при превосходстве врага**: если враг сильнее и мы в его
   радиусе — среди доступных ходов выбирать тот, что увеличивает
   дистанцию, а не любой "подальше".
3. **`MoveDefensivelyScr`**: отступление буквально к своему городу/базе
   (конкретная точка), не абстрактное "куда-то в сторону".

## Рекомендованный путь (от дешёвого к дорогому)

### Шаг A — дешёвый, без симуляции (затрагивает только порядок исполнения)
В `attackState.execute()` применять решение каждого юнита (хотя бы
изменение HP цели в локальной копии/счётчике) сразу после того как оно
принято, ДО того как решается следующий юнит. Тогда `scoreTarget()"
следующего юнита увидит уже подбитую этим ходом цель и сам, естественно,
предпочтёт добивающий удар — без отдельного "группового" правила.

### Шаг B — мелкие портативные правила
Добавить в `scoreTarget()`/`bestStepToward()` две эвристики из списка
выше: проверку ответного удара перед атакой, и явное предпочтение
увеличения дистанции при отступлении от более сильного врага (вместо
текущего "куда получится"). Это прямое расширение модуля `Flee`.

### Шаг C — наст. lookahead (только если Шагов A/B не хватит)
Одношаговая симуляция по образцу `OneStepLookAheadAgent`/`MilitaryFunc`:
скопировать минимально нужный кусок состояния (атакующий + цель +
участвующие в этом шаге юниты), применить кандидатное действие на копии,
сравнить результат с альтернативами. Это уже близко к тому, что в
`architecture.md` записано как "TODO крупный" (#23) — обобщённый слой
выбора цели. Сравнимо по объёму с отдельной сессией, не делать
мимоходом.

### Блокер: ADB/ATB/AAF/WSS не имеют поля `atDamage` в `classTemplates.js`

В `units.js` конструкторе есть фоллбэк `this.atDamage = options.atDamage || 1`.
Поэтому СЕЙЧАС эти четыре класса бьют на `1` урона — наравне с самым
слабым юнитом в игре, а не как "хрупкий но опасный" архетип, который
запланирован. **Это нужно поправить до того, как dangerScore станет иметь
смысл** — иначе вес есть, а зубов нет.

### Новая механика: авиация как расходники (AAF/ADB/ATB)

Подтверждено пользователем, НЕ реализовано в коде:
- не получают ответный урон при атаке (атакуют беспалатно, без риска)
- живут ограниченное количество ходов
- после исчерпания — пополнение спаунится около живого WCA

Из этого следует важный стратегический вывод: **WCA — самая ценная цель
во флоте**, важнее даже самих бомбардировщиков. Потопить носитель =
отрезать пополнение всей будущей авиации, не просто убить один юнит
(аналогия — Тихоокеанский театр WWII).

Это тянет на отдельный пункт в `known-issues.md`/`architecture.md` —
нужны как минимум: счётчик ходов жизни юнита, привязка точки спауна к
конкретному живому юниту-носителю, и булевый флаг "не получает ответный
урон" в модулях.

### Урон по классу цели — архитектура (2026-06-21)

Цель: разный урон одного и того же оружия против разных типов целей
(например, `Main` у WBB: 10 по кораблям, минимально/0 по самолётам), но
без взрыва сложности (НЕ таблица "юнит × юнит") и так, чтобы апгрейды
оружия (будущая система прогрессии/veteran) каскадировались бесплатно,
без переопределения юнита.

**Реальная Polytopia, для сверки**: "не получает ответку" существует в
двух независимых формах одновременно — (1) дистанционно/эмерджентно,
просто из сравнения range атакующего и защитника (бесплатно, уже
работает через существующую логику), и (2) явный флаг-исключение у
конкретного юнита, не зависящий от дистанции — в реальной игре так
устроен Phychi (особое племя Cymanti). Для ADB/ATB разумно начать с (1);
явный флаг (2) держать в запасе, если дистанционной логики где-то не
хватит.

**Три слоя, каждый — единственное место правды:**

1. **Класс цели** — атрибут юнита-ЦЕЛИ, один раз в `classTemplates.js`:
   `targetClass: 'surface' | 'air' | 'sub'`
2. **Урон по классу** — атрибут ОРУЖИЯ (не юнита!), один раз в
   `weaponTypes.js`: `damageVs: { surface: 10, air: 1, sub: 0 }`.
   Отсутствие категории в объекте = оружие вообще не может выбрать такую
   цель (не просто 0 урона — невозможность атаки).
3. **Текущий набор оружия юнита** — уже существующий `weType` массив,
   просто список "что есть сейчас", без чисел внутри.

Реальный урон в бою = `max` по всем `weType` юнита из
`weaponTypes[w].damageVs[target.targetClass]` — **та же схема
"перебери массив, возьми лучшее"**, которую уже использует фикс бага #21
для `atRange` (там для дальности, тут для урона — один и тот же паттерн,
разные поля). Из этого бесплатно следует: если юнит получает новое
оружие через будущую прогрессию (например WCC получает `'Torp'`, WBB
получает `'Small'`) — он автоматически наследует всё, что умеет это
оружие, включая урон по новым классам целей, без переопределения самого
юнита где-либо. Цифры урона живут только в `weaponTypes.js`, юниты
только ссылаются на список оружия.

**Уточнение 2026-06-21 — `damageVs` должен быть МНОЖИТЕЛЕМ, не
абсолютным числом.** В текущих данных `atDamage` уже привязан к ЮНИТУ
(WDD=2, WCC=3 — уже разные), а `weType`/`weaponTypes.js` сейчас отвечает
только за дальность и блокировку LoS, не за число урона. Абсолютный
`damageVs` на оружии стёр бы эту уже существующую разницу (Small у WDD и
Small у WCC стали бы давать одинаковый урон). Правильная формула:

```js
// weaponTypes.js
Small: { damageVs: { surface: 1.0, air: 0.3, sub: 0 } } // множители, не числа
```
```js
реальный урон = unit.atDamage * weaponTypes[w].damageVs[target.targetClass]
```

WDD-Small по воздуху = `2 × 0.3`, WCC-Small по воздуху = `3 × 0.3` —
разница между юнитами сохраняется автоматически, правило "насколько
эффективен Small против воздуха в принципе" всё равно живёт в одном
месте (на оружии). Отсутствие категории в объекте = не может выбрать
такую цель вообще (не 0 урона, а невозможность атаки).

### Авиация: дальность атаки vs "не провоцирует ответку" — это два разных свойства

Подтверждено реальной игрой (Cloak → Daggers, см.
https://polytopia.fandom.com/wiki/Cloak): <i>"Daggers... do not take
retaliation when attacking"</i> — точная аналогия пользователя: WCA = механизм
спауна (как Cloak), ADB/ATB/AAF = расходники как Daggers, с тем же
флагом.

Важное решение: чтобы носитель не был imba (сам безопасен + шлёт
безопасные снаряды без всяких рисков), у самолётов должны быть **две
отдельные характеристики**, не одна:

1. **Короткая атакующая дальность** (как у обычного юнита, в упор) —
   заставляет самолёт физически подлететь близко к цели, попадая под
   чужое ПВО/перехват на чужом ходу. Это их риск/баланс.
2. **Флаг "не провоцирует ответку"** (Dagger-style, отдельный от
   дальности) — это их фишка/гиммик.

Без (1) носитель был бы безопасен и его "снаряды" тоже безопасны —
никакого контрплея. С (1) — носитель безопасен, но сами самолёты
перехватываемы (AAF, ПВО WDD/WCC), что и было целью.

### Принцип простоты для игрока (важно, явно запрошено 2026-06-21)

Математика формулы может быть гибкой внутри, но игрок должен ВСЕГДА
видеть целое понятное число урона — как в реальной Polytopia (там даже
калькулятор боя считает промежуточные дробные значения, но округляет до
целого перед показом/применением). Три правила, чтобы не съехать в
сложность:

1. **Округление один раз, в самом конце**, после всех множителей:
   `Math.round(unit.atDamage * weaponTypes[w].damageVs[target.targetClass])`
   — и дальше это просто целое число, как обычный `atDamage`.
2. **Множитель должен быть грубым, 2-3 уровня** (`1` / `0.5` / `0`/нет
   категории), не точные дробные коэффициенты — чтобы правило легко
   запоминалось словами ("Small слабее против воздуха"), а не держалось
   в голове как точная дробь.
3. **Не накладывать несколько множителей друг на друга одновременно**
   (класс цели × бонус территории × ещё что-то). Если позже появится
   ещё один множитель (например бонус территории) — решать порядок
   операций явно в одном месте, не давать им бесконтрольно наслаиваться.

for (const unit of myUnits) {

  const liveTargets = allTargets.filter(t => getAttackDamage(unit, t) !== null);

а не просто что каждая часть существует по отдельности.

## Ветеранство / дремлющее оружие (2026-06-21)

Идея пользователя: не добавлять оружие юниту динамически при апгрейде, а
держать его в `classTemplates.js` всегда, но с порогом разблокировки по
уровню ветеранства. Пример: у WBB всегда есть `Small` в `weType`, но он
неактивен до достижения veteranLevel.

```js
// classTemplates.js, пример для WBB
weType: ['Main', 'Small'],
weaponUnlocks: { Small: 1 } // Small нужен veteranLevel >= 1; Main доступен с 0
```

Подключается тем же паттерном "перебери массив, возьми лучшее", что уже
используется для `atRange`/`damageVs` — добавляется один фильтр перед
этим перебором:

```js
const usableWeapons = unit.weType.filter(
  w => (template.weaponUnlocks?.[w] ?? 0) <= unit.veteranLevel
);
```

**Блокер**: поля `veteranLevel`/счётчика килов у юнита сейчас не
существует вообще в `units.js`. Нужно завести как новое поле и решить,
что именно повышает уровень (количество килов? выживание N ходов?) —
отдельная маленькая задача перед тем как сама разблокировка станет
рабочей.
