### 1. WBB получил Splash (`b421b89`, `f8529e8` доуточнение)

`combatModules.js` уже описывал `Splash` как ❌ (флаг выставляется, никем

### 2. Fog of war + призраки последней позиции (`63f380f`)

Реализация пустого стаба `world/fogOfWar.js` (known-issues #11, закрыт).
Per-owner два слоя: `explored` (накопительный, никогда не уменьшается) и
`visible` (живой, пересчитывается от текущих позиций юнитов owner'а в
радиусе `viRange`). AI получает `AI_VISION_BONUS=+2` к эффективному
`viRange` (не к бою) — иначе слеп относительно собственных юнитов.

Подключено: `render.js` (только вид player1 — неисследованный террейн не
рисуется, вражеские юниты вне `visible` не рисуются), `attackState.js`
liveTargets и `aiManager.js:findBestTarget` (Percy) — AI не может
целиться в то, чего не видит. Карта (`mapIndex`) НЕ прячется вообще —
известна целиком с начала партии всем, скрыты только текущие позиции
вражеских юнитов.

**Призраки** — когда враг, которого только что видели, пропадает из
`visible`, его последняя позиция остаётся полупрозрачным маркером на
1 полный ход (`GHOST_TTL=1`). Debugging-момент сессии: старение `ttl`
изначально стояло прямо в `updateVisibility()`, которая вызывается МНОГО
раз за ход (у player1 — на каждый `redraw()`), поэтому призрак истаивал
за пару кликов вместо полного хода. Исправлено разделением на
`updateVisibility()` (живой пересчёт + появление призрака) и
`expireGhosts()` (старение, вызывается РОВНО раз за старт хода owner'а).

### 3. WBB `viRange` 100 → 6 (`f8529e8`)

Найдено при первом визуальном тесте — тумана не было видно вообще. `viRange:100`
был безобидной цифрой-плейсхолдером, пока поле нигде не читалось; один
WBB (всегда есть в стартовом флоте игрока, `dominator.js:FLEET`) сразу
открывал всю карту целиком (`size:10` по умолчанию, максимум ~20 гексов
от центра). Снижено до 6, совпадает с его же `atRange`.

### 4. Подсветка атаки гейтится туманом (`e58f283`)

Второй визуальный баг того же теста — подсветка возможности атаки
светилась даже в тумане. Причина: `mechanics/units.js:getAttackableHexes()`
не знала о видимости вообще, а её же использует `handleCanvasClick()` для
валидации реального клика-атаки — то есть игрок теоретически мог бы
атаковать вслепую, не только видеть лишнюю подсветку. Один фильтр
`isVisible()` в этой функции чинит оба проявления сразу.

### 5. Terrain movement cost — deep/surf штрафы по классам (`13758cd`, round-up фикс `38e2f95`)

Дизайн пользователя (переоткрыл отложенную идею из project-memory
"Terrain modifiers"): капиталшипы хуже держатся на мелководье, мелкие
корабли — в глубокой воде, submarine вообще не умеет на мелководье.

| Класс | surf | water | deep |
|---|---|---|---|
| WBB | штраф (cost 2) | ok | ok |
| WCC | ok | ok | ok |
| WDD | ok | ok | штраф (cost 2) |
| WCA | штраф (cost 2) | ok | ok |
| WSB | не может вообще | ok | ok |

Новое поле `unit.terrainCost` (`{terrain: cost}`, дефолт 1) — независимый
слой от `moveTerrain` (что разрешено vs что сколько стоит). `getAvailableHexes()`
и `pathfinding.js:findPath()` переведены с BFS на честный Dijkstra — с
весом шага "нашли раньше = дешевле" перестаёт быть гарантией.

Два новых модуля в `navigationModules.js` — не переиспользовали `Navy`
напрямую, его `effect()` даёт `deep` СВЯЗАННО с `+1 moRange`, что для
WDD/WCA было бы случайным баффом скорости вместо штрафа:
- **`Draft`** — открывает `deep`, без побочного эффекта на скорость (WDD, WCA)
- **`Submerge`** — `water`+`deep`, без `surf`, тот же `-1 moRange` что у
  `Sail` (WSB, заменяет `Sail` целиком)

**Round-up фикс** (по цитате пользователя из вики Polytopia: "even if you
have 0.5 movement points remaining, you can still move onto a tile
costing 1 or even 3") — юнит всегда может сделать последний шаг, даже
если формально не хватает остатка бюджета, лишь бы что-то оставалось ДО
шага. Первая версия сессии была строже (блокировала шаг впритык), из-за
чего юнит с 1 очком из 3 не мог зайти на deep(cost 2) вообще — играло
неинтуитивно, разработчик не мог объяснить в одном предложении.

**Побочные находки при ревизии всех шаблонов под эту работу:**
- WDD/WCC/ASP хранили мёртвое поле `moveTerrain: [...]` в `classTemplates.js`
  — конструктор `Unit` его никогда не читал (реальный `moveTerrain`
  строится только из `modules`). Удалено.
- WSB: `spawnTerrain` включал `surf`, а старый `moveTerrain` (через
  `Sail`) — нет; юнит мог заспауниться там, откуда физически не может
  уйти. Исправлено заодно с переводом на `Submerge`.
- `WSS` обнаружен вообще без `modules` в шаблоне → не может двигаться ни
  по одному террейну прямо сейчас. НЕ чинили (не по теме) — known-issues #30.
- `Navy`-модуль: `description` говорит "+1 к дальности атаки", код даёт
  "+1 moRange". Не совпадают, не правили ни то ни другое — весь баланс
  флота калиброван под текущий код.

## Найдено, но НЕ исправлено (открытый бэклог)

### Авиация one-shot'ает эскорт (known-issues #31, новый)

Прогон `getAttackDamage()` по факту: `ADB → WDD(10hp) = 16dmg`,
`ADB → WCC(12hp) = 14dmg`, `ATB → WDD = 12dmg` — гарантированный килл за
1 удар, `noCounter:true`, то есть вообще без риска для атакующего. Тот же
паттерн one-shot, что чинили для WBB в сессии 8 (DEF < ATK), только для
целей авиации (`WDD.def=2`, `WCC.def=3`) никто не проходил методологию
hits-to-kill при добавлении `atDamage` 5/4 у ADB/ATB.

**Решение согласовано с пользователем, не реализовано в этом коммите**:
снизить мощность авиации + завести fuel-механику (уточнить у пользователя
в следующей итерации — это расширение уже существующего `lifeTurns`
(тикает, юнит исчезает) или отдельный, новый по смыслу ресурс).

### WCC чуть сильнее сестёр по hits-to-kill

Матрица (без контратаки): WDD→WCC=3, WCC→WDD=2; WDD→WBB=4, WBB→WDD=2;
WCC→WBB=3, WBB→WCC=2. WCC убивает обоих за 2 удара, сам умирает за 2-3 —
не катастрофа, но самый эффективный класс тройки. Не трогали, только
зафиксировано наблюдением при разборе статов.
